# 多趣味サポートアプリ 企画・仕様書
## 1. 企画概要

複数の趣味に割く時間を、「好みの割合（％）」から週間の時間割として自動提案してくれる、多趣味サポートアプリ。

### 解決したい困りごと

- 多趣味をバランスよく楽しみたい（一つの趣味に偏りすぎてしまう）
- ズボラで、自分で計画を立てるのは面倒
- タスク管理をするほどではないが、ざっくりとした計画性は欲しい

### 競合との差別化

| サービス | 特徴 |
| --- | --- |
| Structured | 1日のスケジュールをブロック状に提案・管理。やるべきことを入力すればスケジュールを組み立てられる |
| マイルーティン | 毎日の決まった行動（起床・通勤・食事・睡眠など）をテンプレート化し、ルーティンごとのスケジュールを提案 |
| **本アプリ** | 「毎日のスケジュール」ではなく、**毎週の自由時間に限った趣味の割り振り**に特化。ユーザー操作は「自由時間の入力」と「趣味の時間配分（％）を決める」のみ。唯一の正解を計算するのではなく、**複数パターンの時間割案を提示**し、ユーザーが参考にして選ぶ形をとる |

---

## 2. 使い方フロー

1. **時間を割きたい趣味**を、円グラフに入れたいだけ入れる（例：ゲーム、ジム、ペットと遊ぶ、漫画を読む）
2. 円グラフ上で、**それぞれの趣味に割きたい時間の配分（％）**を決める（合計100%）
3. **１週間の自由時間**を、曜日ごとに15分刻みのスライダーで入力する（入力の保存と次画面（結果発表）への遷移は1つのボタンに統合されており、別途更新操作を行う必要はない）
4. アプリが自由時間の実際の値をもとに、曜日への配分の仕方が異なる**5パターン**の時間割案を自動生成する（詳細は5章参照）
5. ユーザーは5パターンをキャッチコピーと一緒に見比べ、参考にしたいものを選ぶ（唯一の正解を選ぶのではなく、あくまで参考提示）
6. 気に入ったパターンを選択すると、そのスケジュールが保存され、TOPページでいつでも確認できるようになる（保存できるのは常に1つのみ。新しく選び直すと上書きされる）

## 3. ユーザー操作・入力項目（確定版）

UXを「ズボラでも迷わず完了できる」ことを最優先し、ユーザーの入力項目を以下の2つだけに絞る。

| 入力項目 | 内容 |
| --- | --- |
| 自由時間 | 曜日ごとに15分刻みのスライダーで入力（例：月＝1時間30分、土＝5時間） |
| 趣味の配分％ | 円グラフに趣味を追加していく形式。円グラフは100%からスタートし、趣味を登録するたびに100%を自動で割り振っていくため、ユーザーが手動で合計を100%に揃える必要はない |

### 見送った入力項目（旧仕様からの変更点）

以前は「頻度」「曜日・配分の偏り」「最低確保時間」を趣味ごとに個別設定させる方式を検討していたが、ユーザー操作を最小化する方針への転換に伴い、以下はすべてユーザー入力から外し、システム側のロジック（5章）で自動的に扱う形に変更した。

- **頻度（毎日／週○回など）**：個別指定を廃止。テンプレートパターンの配置ロジックの中で自動的に決まる
- **曜日・配分の偏り**：個別指定を廃止。「配置の集中度」軸（休日集中型／平日分散型）としてテンプレート側に統合
- **最低確保時間**：廃止。優先順位は配分％の高低のみで自動判定する（5.2参照）

---

## 4. 見送った機能：最大時間（上限）

### 検討経緯

「趣味時間の使いすぎ防止」の目的で最大時間の設定を検討したが、以下の理由から**v1では不採用**と決定。

- 本アプリは「複数パターンを提案してから、ユーザーが自分の好みに近いものを選ぶ」思想が土台にあり、上限機能と役割が重複する。
- 「最低確保時間（守りの安心感）」と異なり、「最大時間（律する方向の設定）」はズボラ層にとって入力動機が弱く、使われない可能性が高い。
- 実装・検証コストが増える割に効果が見合わない。

### 今後の扱い

v1ではカットし、リリース後に実際のユーザーの声（「特定の趣味の配分が多くなりすぎて困る」等）が出てきた場合に、v2で「上限スライダー（目安値からの任意調整）」として追加検討する。

## 5. スケジュール提案ロジック

### 5.1 提案パターン（確定：5パターン）

配分％の高低から優先順位を自動判定しつつ、以下の5パターンを並行して算出する。**曜日ラベル（土日／平日）には一切依存せず**、その週に実際に入力された自由時間の値だけを基準にパターンを算出する（詳細ロジックは5.4参照）。

| パターン | キャッチコピー | 曜日配分の考え方 |
| --- | --- | --- |
| A | 時間をかけたいことは、時間のある日に。 | 自由時間が多い曜日から優先し、優先度の高い趣味から順に埋めていく |
| B | 時間をかけたいことは、毎日の日課に。 | 自由時間が少ない曜日から優先し、Aと同じ手順で埋めていく |
| C | やりたいことを、毎日少しずつ。 | 全曜日に対して、週の目標時間を自由時間の割合に応じて比例配分する |
| D | 時間のある日に、好きなことを分け合おう。 | Aと同じ曜日順序だが、自由時間が同値の曜日はグループとして公平に配分し、1曜日に収まりきらない場合は次点の趣味と配分％の比率で分け合う |
| E | 毎日の日課に、好きなことを分け合おう。 | Bと同じ曜日順序で、Dと同じ配分ルールを適用する |

### 5.2 優先順位（自動判定）

ユーザーに優先度を直接選ばせず、**配分％が高い趣味ほど優先度が高い**とみなして自動判定する。

### 5.3 算出ステップ（2段階丸め方式）

時間の割り振り単位は15分とし、端数は「最大剰余法」で丸める。日ごとに毎回丸めると誤差が積み重なるため、**週単位で先に丸めてから曜日に配分する2段階方式**を採用する。

1. **総自由時間の算出**：1週間の自由時間（15分刻みで入力済み）の合計を算出する。
2. **最低限必要な自由時間の確認（エラー判定）**：週の自由時間合計が、登録趣味数×15分に満たない場合はエラーとし、提案を行わない（6章参照）。
3. **週の目標時間の算出**：各趣味について「週の自由時間合計 × 配分％」で目標時間（分）を算出する。
4. **週の目標時間を15分単位に丸める**：各趣味の目標時間を15分単位の整数部分で確定し、余りの単位を端数（小数部分）が大きい趣味から順に1単位ずつ配分する（最大剰余法）。丸め後の合計が自由時間合計と一致するように調整する。なお、端数が同点の趣味が複数ある場合は、①配分％が高い方、②それでも同点なら先に登録された趣味（登録順が早い方）、の順に優先して単位を配分する。
5. **0分になった趣味への救済**：Step4の時点で0分になった趣味がある場合、その趣味1つにつき1単位（15分）を、その時点で最も多くの時間を保持している趣味から譲り受ける。譲り渡す趣味の候補が複数（同率で最多）ある場合は、①登録時の配分％が低い方、②それでも同率なら登録順が遅い方（IDが大きい方）、の順に優先して徴収する。0分の趣味が複数ある場合は、対象ごとにこの手順を繰り返す。

上記Step1〜5は、A〜Eすべてのパターンに共通する処理であり、ここで確定した「趣味ごとの週の目標時間」を土台に、5.4で曜日ごとに配分する。

### 5.4 曜日への配分ロジック（パターンごと）

#### 5.4.1 共通の準備

- **曜日のソート**：自由時間が多い順（A・D）または少ない順（B・E）に曜日を並べる。自由時間が完全に同じ値の曜日は「同値グループ」としてまとめる。同値グループ内の並び順、および同値どうしの端数タイブレークは、曜日番号（日=0→月=1→火=2→水=3→木=4→金=5→土=6）の早い順とする。
- **趣味のソート**：配分％の高い順に並べる。同率の場合は、登録が早い趣味（IDが若い方）を優先する。

#### 5.4.2 パターンA・B：逐次グリーディ方式

ソートした曜日の並びに沿って、優先度の高い趣味から順に、曜日の自由時間を使い切るまで詰めていく。1つの趣味の目標時間を使い切ったら、次の優先度の趣味にバトンタッチし、直前の曜日の余りから続きを詰める。同値グループであっても特別な処理はせず、曜日の並び順通り、1曜日ずつ機械的に埋めていく。

#### 5.4.3 パターンC：比例配分（繰越キャリー方式）

曜日を「日→月→火→水→木→金→土」の固定順で1日ずつ処理する。

1. 各趣味の「週の目標時間の残り（R）」を用意する（初期値はStep1〜5で確定した週の目標時間）。
2. その日の理想配分（小数） = R ×（その日の自由時間 ÷ その時点で残っている自由時間の合計）
3. 15分単位に丸める（最大剰余法。端数同点時のタイブレークは曜日番号の早い順）。その日の配分合計が、その日の自由時間とぴったり一致するように仕上げる。
4. 配分した分を、各趣味の残り（R）から差し引く。
5. 次の曜日へ進み、2〜4を繰り返す。最終曜日（土）では、残っている自由時間と残っている趣味の目標時間の合計が必ず一致するため、丸め処理なしでそのまま割り当てる。

#### 5.4.4 パターンD・E：グループ公平配分方式

ソートした曜日の並びに沿って処理するが、A・Bとは異なり、**同値グループの中では趣味の時間を公平に按分**する。

1. 現在の同値グループ（1日だけの場合を含む）に対して、現在の最優先趣味の残り時間を、そのグループの日数で割った「フェアシェア（1日あたりの均等配分額）」を計算する。
2. **フェアシェアがグループの1日あたりの自由時間の枠に収まる場合**：グループ内の全曜日に、このフェアシェアを均等に配分する（15分単位にならない場合は最大剰余法で丸め、曜日間の端数タイブレークは曜日番号の早い順）。この趣味の残り時間は0になり、枠に余りがあれば次の優先度の趣味へ処理を移し、同じグループの残り枠に対して同様の配分を行う（複数の趣味が同じグループ内で重なることがある）。
3. **フェアシェアが1日の自由時間の枠を超える場合（＝そのグループだけでは使い切れない場合）**：ここで比較する「1日の自由時間の枠」は、そのグループを定義している手つかずの状態の1日あたりの自由時間（同値グループ内で共通の値）であり、他の趣味が先に使ったあとの「その時点の残り枠」ではない。この判定は、その趣味がグループに入ってフェアシェアを計算した最初の時点で一度だけ行われ、一度Step2（収まる場合）に分類された趣味は、その後の配分で特定の曜日の残り枠が偶然足りなくなっても、比率分割ではなくStep2内のカスケード処理（その曜日を打ち止めて次の曜日へ回す）で対応する。現在の趣味と次点の趣味の「配分％の比率」で、その日（グループ全体）の枠を分け合う。グループが複数曜日から成る場合も、比率分割は常に曜日ごとに個別に行う（グループの総量を先にまとめて按分するのではなく、対象となる曜日1つ1つに、その時点の残り枠を基準に同じ配分％比率を適用する）。この比率計算が15分単位にきれいに割り切れない場合は、最大剰余法で丸め、端数が同点の場合のタイブレークもStep4・5.4.1と同じく①配分％が高い方、②それでも同点なら登録が早い方（IDが若い方）、の順に優先して単位を配分する。現在の趣味はまだ残り時間があるため、次のグループにも引き続き最優先趣味として参加する。次点の趣味についても、実際に必要な量より多く割り当てられていないか確認し、必要なら余りをさらに次の趣味へ回す。
4. 次の曜日グループへ進み、1〜3を繰り返す。最終グループでは、残っている自由時間と趣味の残り時間の合計が自動的に一致する。

**A・BとD・Eの違い**：A・Bは曜日の並び順通りに機械的に埋めるだけなのに対し、D・Eは同値グループ内で公平に按分し、1日に収まりきらない場合も次点の趣味と分け合うため、より「なだらか」な配分になる。

### 5.5 全パターン共通の算出フロー

5.4.2〜5.4.4を、A〜Eの5パターン分、並行して算出し提示する。

## 6. エラーハンドリング

入力項目を「自由時間」「配分％」の2つに絞ったことで、旧仕様にあった頻度・曜日指定に起因するエラーケース（「休日のみ指定で週3回は設定できない」等）は発生しなくなった。

### 配分％の合計不一致について（エラーハンドリング不要）

配分％は、円グラフ100%を起点に、趣味の登録数が増えるたびに100%を自動で割っていくUI/UXを想定している。ユーザーに手動で100%へ揃えさせる負担をかけない設計とするため、「合計が100%にならない」というエラーケース自体が発生しない。よってこの点のエラーハンドリングは不要。

### 週の自由時間が不足するケース

| ケース | 対応 |
| --- | --- |
| 週の自由時間合計が、登録趣味数に対して最低限必要な時間（登録趣味数 × 15分）に満たない | 具体的な不足分がわかるメッセージを表示し、スケジュール提案を行わない（例：「最低60分（登録趣味数×15分）の自由時間を登録してください」） |

## 7. パターン表示・結果画面の設計方針

- 5パターンをキャッチコピー付きで一覧表示し、ユーザーがスクロールしながら比較できるようにする（複数パターンを並べて見比べたいというコンセプトとの相性を優先し、タップでの切り替え表示から変更）。
- 各パターンの中身は、8章のような**曜日別の時間割表**（趣味ごとの時間、自由時間なしの日は❌）で表示する。
- 15分丸めによる目標％からの誤差は最大でも数分程度に収まるため、旧仕様で検討していた「ズレの伝え方（ことば＋アイコンの4段階表示）」のような大掛かりな仕組みは廃止する。誤差が気になる場合は、小さな注記程度に留める方針とする。

### 7.1 パターンの選択・保存

- 各パターンには「これに決める」のような選択ボタンを設け、ユーザーが気に入ったパターンを選べるようにする。
- 選択したパターンの内容（キャッチコピー・趣味ごとの曜日別スケジュール）を保存する。保存できるスケジュールは常に1つのみとし、TOPページで一意に表示する。
- 既に保存済みのスケジュールがある状態で新しく選択した場合は、「スケジュールを上書き保存しますか？」の確認を挟んでから上書きする。
- 保存時、趣味名は文字列としてスナップショット保存する（趣味オブジェクトそのものへの参照は持たない）。後から趣味の登録内容を変更・削除しても、保存済みのスケジュール表示は影響を受けない。趣味や自由時間を変更したい場合は再度診断をやり直す想定で、その場合は新しいスケジュールがTOPページの内容を上書きする。

### 7.2 再診断

- 結果発表画面には「再診断をする」ボタンを設置し、押すと趣味一覧画面（趣味登録）に遷移する。
- 遷移時に既存の趣味データは削除されない。ユーザーはそこから趣味を編集・追加・削除し、自由時間入力を経て、再度結果発表画面に進むことができる。
- 結果発表画面は、表示するたびにその時点の趣味・自由時間データをもとに5パターンを計算し直す。

## 12.技術選定

- 環境構築：docker
    - お馴染みの相棒
- **バックエンド**：Ruby on Rails
    - **Railsの学習を一段深める**のにちょうどいい題材
    - Rails8を使ってみたかった
- **フロントエンド**：**Hotwire（Turbo + Stimulus）**
    - 円グラフの％調整、5パターンの比較画面の切り替えなど、このアプリで必要な「画面の一部だけ更新する」系のUIと相性が良い
- データベース：**SQLite**
    - Rails 8のデフォルト。趣味登録・週間の自由時間の登録ぐらいならこれで十分
- デプロイ：render
    - 無料かつ、デプロイ経験がある環境であるため

## 13. TOPページの設計方針

- アプリのトップ（ルートパス）は、選んだスケジュールを確認できる専用ページとする。
- 保存済みのスケジュールがある場合：選んだパターンのキャッチコピーと、曜日別の時間割表を表示する。
- 保存済みのスケジュールがない場合：「まだ趣味スケジュールはありません」というメッセージを表示する。
- あわせて、アプリの簡単な説明・使い方の案内も表示し、初めて訪れたユーザーが迷わないようにする。
